# 任务复盘台账

这份台账按可理解的任务片段整理，覆盖项目主要阶段，不是所有 commit 或所有聊天轮次的逐项清单。编号为本次复盘编号，不改动历史记录。

## 怎么判断正反例

采用结果分档，不做会话总分或模型排名：

- **明确认可**：用户明确说某个功能已经成功或合格；认可只覆盖所说部分。
- **实现证据**：有提交、产物或当日验证记录；不等同于用户验收。
- **需返工**：同一要求仍未达到，或改动造成回退。
- **范围纠正**：讨论对象、实施时机、工作目录被理解错。
- **新需求**：新的使用场景或取舍，不直接算上一轮失败。
- **外部阻塞／待核验**：运行中断或缺少后续证据，不强行计正负。

“正向”与“负向”只指具体片段的经验。比如同一条话说快捷标签不错、拖动没好，要分成两个结果。以下技术根因若来自历史审查，会明确标注；本次没有逐个重新运行旧版本。

## 从台账得出的优先级

最应该先固化的是：**恢复上下文、限定修改范围、验证完整操作路径、区分代码与交付状态**。它们出现在多个阶段，也都有可执行的下一步。

不应从这份台账推出“UI 任务都失败”“必须永远只处理一条问题”“不能使用子代理”或“应该换某个模型”。本表有意挑选能说明经验的案例，既非随机抽样，也不是全部任务清单，不能据此算成功率。
