# 2026-10-18 归档流程走查

状态：用户实操反馈与初步分析；尚未形成实施方案。本轮仅记录和阅读源码，未修改产品代码、运行交互验收或打包。源码观察不代表用户正在运行的安装包行为。

## 样本一：天女兽

用户已归档 90 多张卡，本次准备完整重走归档流程。第一张为小体量、已有整理成果的旧卡；后续另选近期卡片补充完整流程。

### 用户报告的操作

1. 角色库选择“同人”类型，按评分排序，打开未评分的“天女兽”。
2. 点击“处理”打开故事文件。
3. 快速添加正则，删除 `<StatusBlock></StatusBlock>` 包裹的状态栏，保留最近 20 楼，并应用到原文。
4. 聊天发生于 2024 年，129 段、约 2.9 万字。已经生成过总结和日记，直接复制，并手工删除总结、日记以外的多余内容。具体复制来源入口未明确。
5. 返回详情页，分别切到总结、日记，手动录入 1 篇第一卷总结、2 篇角色日记。
6. 以前的笔记库中已有总结，世界书中也保存过总结与日记条目。
7. 评为 6 分，添加“纯欲类”“调教”标签，更新角色卡简介。后续继续游玩可能性较低，不生成角色档案，相关内容放入备注。
8. 尝试通过 Nebius 的 DeepSeek 模型生成故事树。用户反馈：有时拒绝生成，希望支持预设；详情页预览不直观；希望把已有总结、日记等资源加入上下文。未提供具体模型 ID、失败响应或截图，尚不能确定拒绝原因。
9. 用户认为本卡基本完成，但体量小，未覆盖全部归档步骤。

### 源码核对

- `src/components/chat/RegexQuickAdd.tsx`：快速添加负责生成标签清理规则，不提供楼层范围；新增规则不带深度限制。范围在 `RegexDepthEditor.tsx` 设置。
- `src/components/chat/RegexSidebar.tsx`：已有规则集预设保存与加载，应优先评估现有复用入口，不能直接判断为缺少复用能力。
- `src/components/character/StoryRecordsView.tsx`：总结和日记按当前类型分别手动录入；故事树为只读递归大纲，正文截为三行，完整内容挂在悬浮提示中。
- `src/lib/story-tree-ai.ts` 与 `src/components/story-tree/AIFillDialog.tsx`：生成请求包含当前树大纲、选定聊天正文、额外要求及可编辑提示词，没有挂载 ST 预设、总结或日记正文的参数。确认应用时读取已有分卷，只用于选择卷号标签。
- `src/components/organize/RecordWorkbench.tsx`：总结/日记生成工作台已有预设、世界书及前情选择相关组件，可作为后续复用依据；本次未验证交互。

### 初步优化候选（待下一样本检验）

1. 清理规则创建与范围设置放在同一处完成；常用规则连同范围复用。最近 20 楼是本样本选择，尚不是全局默认要求。
2. 减少已有成果的搬运：从选中文本直接存为总结/日记、连续录入多篇、从关联世界书选择条目转存等方案待比较。优先让用户选定已有版本，不把笔记与世界书的重复内容全部导入。
3. 故事树分别处理生成配置、上下文选择、详情页阅读三个问题。总结可辅助提炼结构，日记要保留人物视角，避免把主观内容当作客观剧情事实。
4. 观察是否需要“下一张未评分”入口及筛选、排序、滚动位置恢复；当前只证明用户用未评分卡挑选处理对象，不能认定评分就是归档完成状态。
5. 允许不同归档深度。本卡以清理正文、保留已有成果、评分标签和备注完成收尾；不宜把角色档案、故事树等都设为必做项。

## 下一样本观察点

- 新生成总结、日记与已有成果复用相比，哪些步骤相同，哪些增加了操作负担。
- 哪里反复返回、重选故事或楼层范围、重复输入设置；保存后如何确认已完成。
- 每次复制的来源与目标；已有资料是否同版本、是否需要更新。
- 故事树生成失败时的原始提示，以及预览中最难看清的内容。
- 完成后返回角色库，定位下一张卡是否顺畅。

这些是观察点，不是要求用户逐项执行的测试清单。

## 样本二：近期长篇卡（名称未提供）

用户完成实操约 1.5 小时。以下楼号、字数、token 数及模型名称均按用户记录，未读取真实故事核验；生成插入消息后楼号可能变化，不能自行把初始范围当作最终范围。

### 用户报告的操作与结果

1. 从 SillyTavern 导出角色卡与聊天，再导入 STE。作者的 MVU 变量有问题，用户此前自行修复；初始故事共 496 段聊天。
2. 正则删除结束标记 `</think_nya~>` 之前的内容，并应用到原文。用户输入的正则描述为 `\</think_nya\~>`，本记录不推断具体匹配式及是否保留标记。
3. 浏览时发现第 26 楼提到的四人群聊后续很少出现，女主舍友后来只提到季云云。这是故事检索、人物追踪需求的实例，不能直接认定剧情矛盾。
4. 分卷范围为第一卷 0–140、第二卷 141–313、第三卷 314–423、第四卷 424–495。
5. 第一卷游玩时已有总结与日记；用户把生成指令存于世界书，阶段结束激活条目生成。希望直接收录为总结/日记，或增加可保存精彩故事的子界面；也提出 Agent 检索关键词、将结果登记到总结/日记的设想。
6. 第二至四卷在 STE 继续聊天中补生成：开启正则和脚本，使用用户所称的“gemini 3.8flash”，先隐藏后续楼层，再启用世界书总结条目，生成总结与日记。
7. 模型目录一直显示第一次同步的模型，没有自动更新。
8. 隐藏的正文变暗，影响继续阅读，需要返回解除隐藏。用户倾向仅标记隐藏状态，或至少支持批量解除。
9. 已选自定义用户角色，但显示名为 `unused`。
10. 处理后正文约 76.4 万字，手动粘贴总结和日记。随后复制故事，测试“小总结正则”：旧楼层只保留随正文生成的小总结；应用后约 9 万字。另记录第一卷总结、日记位于 140–143 楼。
11. 为续玩节省 token，把总结和日记再手动复制进世界书，隐藏前文。世界书约 1.5 万 token。希望批量创建世界书条目、默认 UID 排序且支持倒序、UID 修改后直接生效、世界书自动保存。用户询问这种记忆方式与其他方案的取舍，以及 ST 自定义排序的含义。
12. 用只有小总结的副本生成故事树；“分卷”按钮点击没有明显反应，不清楚用途。
13. 想把树放回 70 多万字的主故事，发现总结、故事/故事树似乎都绑定副本，怀疑错误。明确希望移动入口放在角色详情页，目标为同角色下的其他故事；“故事”在此处指代尚有歧义，不能擅自解释为整篇故事迁移。
14. 导出角色卡与故事再导入本地 ST。详情页的 JSON 文件导出失败；SillyTavern JSONL 较大，处理区导出较小；用户很少用“更多导出与清理”。角色卡导出未选位置，也无成功提示。
15. 导回 ST 后聊天正常，但卡仍绑定修改前世界书。用户发现修改保存在派生书，希望旧版留作备份，修改后的世界书成为当前角色卡内置版本。
16. 收尾评分 9.5：卡本身一般，但人设符合喜好，成品故事也好。建议去掉故事单独评分；添加标签，使用 Genspark 生成立绘并导入。为节省时间，未同步旧 Obsidian 库。

### 两个样本共同指向的流程改进

- 聊天生成/已有文本 → 收录记录 → 批量写入世界书 → 导出角色卡。这条成果流转链比增加新的生成入口更优先；条目需要保留故事、类型、卷次、角色视角和来源楼层。
- 阅读显示、发给 AI 的范围、是否永久清理正文应可分别控制。本次隐藏后续是为指定总结范围，隐藏前文是为续玩记忆预算，两者目的不同。
- 小总结可以作为同一故事的 AI 输入方式；76.4 万字全文仍用于阅读。若能直接选择输入方式和成果目标，可减少仅为压缩而复制故事、再搬回成果的步骤。这是方案候选，尚未实施。
- 详情页应提供同角色故事间的成果移动入口，并覆盖总结、日记、故事树；区分真正移动与复制。
- 用户已明确的方向：自动保存世界书、UID 默认排序及倒序、免单独应用 UID、角色卡使用当前修改后的世界书、详情页内移动成果。具体保存/导出组合与数据兼容方案尚待设计。
- 故事评分移除、新增摘录/自定义资料子页、Agent 自动收录仍为讨论建议。可先评估已有 DIY 记录能力，而非直接新增重复存储体系。

### 建议实施顺序（讨论稿）

1. 保存、引用与导出一致性；复制后归属及 JSON 导出故障复现。验收必须包含真实入口与导回 ST，特别是修过的 MVU 内容和新增世界书条目。
2. 成果直接收录、详情页移动、批量写入世界书、UID 和隐藏范围操作，减少每卷重复劳动。
3. AI 输入方式、故事树上下文与预览、Agent 登记、自定义资料入口；用实际请求验证 token 与内容，而不是用字数代替。

## 后续讨论：全局 Agent 与归档 skill

### 用户提出的方向

- 记忆沿用此前确定的柏宝书实现方向，避免要求用户额外配置向量模型。
- 将目前参考 PI 的 Agent 工具调用方式扩展到 STE 全局。
- 将固定整理流程写成 skill：自动调用正则保留正文，拆分故事及划卷，组合预设、故事和提示词生成总结，并将成果注册到所属故事。
- 当前属于可行性与设计讨论，尚未批准具体实施方案。“拆分故事”是否指分卷标记或生成多篇独立故事，仍应在设计时区分。

### 当前实现核对

- `src/lib/roleplay/tool-agent.ts` 是 STE 自有的工具调用循环，当前限定 context/memory 两阶段，工具包含搜索、读取、上下文提交和记忆提交；有每轮预算与 120 秒截止时间。本轮检查的 `package.json` 没有直接声明 PI Agent 依赖。参考 PI 的思路不能等同于已内置完整 PI 技能运行系统。
- `src/lib/roleplay/agent-runtime.ts` 将 Agent 绑定到故事/分支的聊天生成与记忆提交生命周期；其持久化校验与日志经验可复用，归档长任务需独立的任务生命周期。
- `src/lib/regex-processor.ts` 已有正则执行；`src/lib/summary-engine.ts` 已有楼层、预设、世界书、模板和前情总结组装；`src/lib/summary-db.ts` 等已有保存接口。缺口主要在工具封装、分卷契约、skill 加载及长任务进度，而非重新实现所有能力。
- `summary-engine.ts` 是独立总结组装器，不等同于完整原 ST 的脚本/宏/变量运行环境。依赖 MVU 或扩展脚本时，应使用相应 ST 运行时路径并独立验证。
- 现行扩展原则记录柏宝书非向量摘要、台账和滑动窗口；当前原版插件通过指定 ZIP 安装。同时存在 STE 原生 Markdown 文件记忆，二者维护归属互斥。因此“借鉴柏宝书的产品方向”“已经兼容的原版插件”“原生文件记忆”不能混称为已统一的实现。
- TauriTavern 预设附带 Agent Skills 元数据，目前保留但未执行；不等于此次提出的 STE 全局工作流 skill 已可运行。

### 初步建议（待讨论）

1. 提供跨页面持续存在的 Agent 入口；每个任务明确捕获库、角色、故事与分支，页面切换不改变正在执行任务的写入目标。
2. skill 表达整理顺序、选用规则、模型/预设/模板以及完成条件；程序提供稳定的读取、正则处理、分卷、生成和成果入库工具。固定步骤由任务执行器记录和推进，需要语义判断的部分再交给模型。
3. 正则处理区分“仅供生成使用的正文”和“应用到故事原文”；默认流程可以复用前者，已指定应用到原文的流程执行后者并保留恢复依据。
4. 分卷按稳定消息身份记录范围，避免生成新楼层后数字错位。整理 Agent 按需读原文、搜索或使用已有摘要；完整生成输入由工具按范围组装，无需反复塞进调度对话。
5. 内容生成复用已配置连接，可与负责工具调用的模型不同。成功入库返回真实记录 ID 并刷新现有总结/日记界面；任务重试不重复生成、重复入库。
6. 全局归档任务不自动成为第二个后台记忆维护者。它可以调用已有非向量资料与记忆能力，仍尊重当前故事的维护归属。
7. 首个候选验收链：一篇长故事 → 正文清理 → 指定范围划卷 → 每卷总结/日记 → 自动绑定原故事；随后扩展批量写世界书、故事树和跨故事整理。
