# 单库卡片容量：当前依据与建议

日期：2026-11-15；执行：Codex。范围：回答容量问题，核对源码与既有证据；没有开展新压力测试或实施性能改动。

## 结论

目前没有经过测试确认的“最多多少张仍不卡顿”。供当前整理决策的保守建议是先按单库几百张（约300–500张）规划、每页24或48张；这是基于实现方式的经验建议，不是测得的上限，也不表示第501张会变慢。上千张是否流畅，需要在指定设备和代表性资料规模下实测，不能从分页或缓存限制直接推出。

11月11日合并记录中的175张卡、245篇故事属于当时的数据规模记录，不是当前实时数量，也不是完整性能验收。10月23日读取范围验证的合成样本为48张卡、96篇故事；它证明按页读取图片、按角色读取故事等行为，不证明千卡容量。此前214篇故事副本、最大3984楼的性能历史也不能换算为角色卡数量上限。

## 当前实现核对

- 默认每页24张，可选12、48、96或不分页；普通分页模式仅渲染当前页卡片。
- 卡面在视口附近按需读取，有图片缓存限额；不会因收藏数量增加就一次显示所有原图。
- 不分页模式直接渲染全部结果；分组模式不参与全局分页，展开大组也会增加卡片组件数量。图片懒加载不等于卡片组件虚拟化。
- 打开文件库仍扫描角色档案、故事目录、记录及资产；故事持久摘要减少未变化故事正文的重复读取，但没有取消目录扫描。
- 角色列表项只去掉原图和立绘，仍包含完整卡片设定等内容；搜索、排序和标签统计在全量角色列表上计算。重设定、内嵌大世界书、多故事和多记录会改变同样卡数下的负载。
- 核对分支`codex/closeout-1110`、HEAD`0720409`；本次核对的角色库页面、索引、文件库后端、查询与图片缓存文件，相对11月12日构建提交`55be2252ce6f`无差异。工作区原有修改保持原状。

源码入口：`src/pages/Library.tsx`、`src/lib/archive-index.ts`、`src/lib/vault/vault-backend.ts`、`src/lib/library-query.ts`、`src/lib/library-tag-preferences.ts`、`src/lib/character-portrait-cache.ts`。既有证据：[10月23日性能验证](../verification/2026-10-23-performance-batch-1.md)。

若后续要求测上限，可用完全合成的500、1000、2000张分档库，分别测打开库、搜索/筛选、翻页、进入角色与返回及内存；实际Windows程序必须遵守独立identifier和构建凭据规则。该方案只是回答中的后续方法，本次没有启动测试、读取真实库、改源码、打包或发布。

对STE的建议仍为讨论：保留可直接搬迁的文件库，增加可重建的轻量目录索引；列表不携带完整设定；用持久索引处理查询、排序与计数；用文件变化校验做增量更新并保留重建入口；将不分页和大分组改为只渲染可见范围；缩略图、正文、搜索索引与后台任务分别限额。SQLite可作为本地可重建索引的候选，不要求把全部资料改成唯一数据库存储，也不以牺牲现有搜索或导出功能换取容量。
