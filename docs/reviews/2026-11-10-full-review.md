## 一、理念

项目有三条写下来的原则，都很清楚：

- **归档是回味，不是数据处理**：不做流程自动化，各功能独立可单用。
- **数据主权学 Obsidian**：明文文件、用户掌控，ST 来源只读。
- **功能贴着 ST 用户的真实场景**，不做脱离需求的东西。

问题是产品已经偏离了自己的说法：

- README 写“只做两件事：归档、编辑处理”，但 0.9.9 实际带着完整的内嵌酒馆聊天、Agent 模式、世界沙盘、主神空间和 GAL。
- README 路线图还列着“Agent 化改造（总结工作流自动编排）”，这正是你 7 月否掉的方向。
- README 徽章是 v0.9.5，实际是 0.9.9；git 标签只打到 v0.9.1。

`CURRENT.md` 里的现行决定已经改成“覆盖浏览、处理与继续游玩”，所以“继续游玩”是你认可的扩展，只是对外的说明没跟上。世界玩法是另一回事，见第四节。

## 三、做得好的地方

- **Rust 文件层很扎实。** 授权根目录、逐级拒绝符号链接、原子写入、永不递归删除、配置键白名单、跨进程配置锁、拒绝覆盖损坏的配置，每一条都有对应测试。
- **类型纪律好。** 非测试代码里 `as any` 为 0，`@ts-ignore` 为 0，`any` 只有 9 处且都有注释；没有死文件（529 个文件全部可达）。
- **内置助手的隔离是认真做的。** 卡片里的脚本放在 `sandbox="allow-scripts"` 的 iframe 里，CSP 禁止联网，只能通过带权限检查的消息接口读写。
- **导入 ST 备份时跳过 `secrets.json`**，不落盘。
- **自定义请求头里禁止出现凭据字段**，诊断快照有 Bearer 脱敏。

## 四、问题

### 1. 验证量很大，但验证的有效性出过大问题

11 月 7 日到 9 日的不稳定，根因是 Codex 桌面版把 AppData 重定向到了自己的容器里。两天里每一份“验证通过”验的都是容器那份配置，不是你双击打开的那份。这件事说明问题不在测试数量：

- 110 个验证文档、44 个一次性脚本，没有一个进 CI。CI 不跑 Playwright、不跑冒烟脚本、不跑 Rust。
- 正式包不写日志（日志插件只在调试版启用）。S4、S5、“配置清空”这几次现场问题都是在没有日志的情况下排查的。
- 界面上看不到构建标识。`release/` 下有二十多个目录的包，出问题时很难确认你运行的是哪一个。

### 2. 世界玩法模块是当前最大的产品风险

- 它在三天内合入，两次提交共改动约 1.2 万行，此前两版被你以“不可玩”否决并回退。
- 0.9.9 的更新日志自己写着“用户可玩性及 Android 真机待验”。我没有找到你实测认可 v3 的记录。
- 入口在聊天页（`ChatHub.tsx:119`），已经随正式包发出去了。
- 它和“归档即回味”的定位距离最远。

这块的代码质量我没审完（子代理中断），只能说产品层面的证据不支持它现在留在主线上。

### 3. 内嵌酒馆与主程序同源，没有沙箱

- 酒馆页面的 iframe 没有 `sandbox` 属性（`Roleplay.tsx:334`），并且直接读 `window.parent` 上的对象（`host-bootstrap.js:14`），说明它和 STE 主界面同源。
- 同时 `tauri.conf.json` 里 CSP 为空、`withGlobalTauri` 打开，HTTP 权限放开所有主机。
- API 密钥以明文存在 `localStorage` 和 `config.json` 里。

内置助手的脚本被关在沙箱里，够不到这些。但用户自己装的**原版酒馆助手和柏宝书是在这个不设防的页面里运行的**，它们加载的卡片脚本理论上能读到密钥、调用文件命令并把数据发出去。这条是我根据上面几处代码推断的，没有做实际利用验证；原版 SillyTavern 本身也有同类暴露，STE 多出来的部分是文件命令和集中存放的密钥。

### 4. 两套 AI 请求实现，旧的那套很薄

- 聊天走 `roleplay/provider.ts`，总结、日记、故事树走 `ai-tools/useOpenAI.ts`。
- 旧的这套没有超时、没有重试、不区分 429 和 502；HTTP 200 里夹带的拒绝、空回复、被截断，统统返回空字符串或一句“API 请求失败”。
- 这和你这几天批量补总结时看到的现象对得上：成功率 40% 到 75%，失败原因要靠外部脚本分类。
- `index.html` 从 Google Fonts 加载字体，离线或国内网络下会失败，也与“本地工具”的说法不一致。

### 5. 测试有盲区

- 42 个生产文件（约 6000 行）从未在不被 mock 的情况下被任何测试加载，领头的是 `CharacterPage.tsx`（798 行）、`AssetSection`、`RatingPanel`、`ChatHub`、`WorldPlay`。
- `st-import.ts`（1302 行）只有 3 个测试文件直接用到；`st-writeback.ts`、`bootstrap.ts`、`tavern-host.ts`、`Roleplay.tsx` 各只有 1 个，其中 `bootstrap` 的 6 个协作模块全被 mock。
- 8 个测试文件是把源码当文本读、断言字符串存在，`frontend-contract` 一个文件就有 238 处这类断言。
- 整个应用没有 ErrorBoundary，也没有全局的未处理异常兜底；有 72 处只写了注释的 catch、52 处 `.catch(() => {})`。

### 6. Rust 层的几处具体缺陷

- **放在 OneDrive 里的库很可能打不开。** 代码拒绝一切重解析点，而 OneDrive 的占位文件都带这个属性。这条是代码加本机属性统计的推断，没有实测。为统计属性我数了你 OneDrive 根目录的条目数，没读文件名和内容。
- 配置锁没有超时：另一个 STE 进程卡住时，这一个会一直等。
- 解压 ST 备份时信任压缩包声明的大小，体积上限可以被伪造的包头绕过。
- 导入用的临时目录没有启动清扫，导入中途崩溃会在临时目录留下最多几个 G。
- 大文件以 base64 整体过 IPC，内存占用是文件的四到五倍。

### 7. 结构上的债

- 状态分散：83 处直接读写 `localStorage`、7 条自定义事件总线、约 30 个模块级可变单例。按库隔离设置就是在这上面补出来的。
- 巨型组件：`NovelView`（1290 行，26 个 state）、`Library`（868 行，29 个 state）、`RecordWorkbench`（26 个 state）。
- 平台判断散落 47 处，另有 4 处绕过了统一的检测函数。
- 库文件没有统一的格式版本号（只在注册表和导入清单里各见到一个 `version: 1`）。这与 1.0 路线图里“格式要工具无关、可迁移”的约束相悖。这条我只做了关键词搜索，没通读数据层。

### 8. 协作过程本身的成本

- 两个 Agent 同时在一个工作区干活，提交要靠临时 index 挑文件。
- `CURRENT.md` 已经长到 4.7 万字符，每次恢复上下文都要读它，而它的大部分是历史。
- 近 300 个提交里修复 135 个、功能 84 个，修复明显多于新增。
