# 批量删除被既有附件路径拦截（2026-11-11）

## 反馈与复现

用户在角色库批量删除时收到“文件检查未完成，已停止删除……已跳过链接或非法路径”。本轮未读取真实聊天、附件正文或正式配置，也未改名、清理或删除真实库文件。

确认的缺陷：`file-maintenance.ts` 在整库引用检查、角色预览、保留清单校验中，使用用于新文件名的严格规则。它拒绝名称末尾的点／空格，而已有附件目录可能含这类名称。因此一处这样的目录即可阻断其他角色的删除。截图的尾部特征与复现相符；未逐项检查用户真实目录属性，不能仅凭截图认定所有报错都不是实际链接。

合成复现包含普通名称、尾点、尾空格、双尾点和混合后缀，同名不同后缀内容互不相同。旧独立Windows构建在真实“角色库→批量管理→删除”入口出现同一错误；8份合成附件字节不变，没有生成回收操作。

## 最小修补

- 仅文件维护流程区分已有路径与新建名称。对已有路径检查时允许合法主体后附点／空格，**路径本身不裁剪、不重命名**。
- 目录预览、整库扫描、内容指纹、移动、回滚及回收站恢复使用相同规则；对其他记录引用的文件继续保留。
- 仍拒绝空段、纯点／空格、`.`／`..`、分隔符、控制字符、设备名、链接；原生层继续检查授权根和每级链接／reparse point。不通过跳过整库校验来解除错误。
- `src-tauri/src/lib.rs`仅增加测试，无Rust运行逻辑变更。用真实Windows文件验证canonical根下名称精确性：`package`、`package.`、`package `、`package..`不会互相替代，移动／恢复内容一致。

排查也发现`safeName`先去尾点再截断，长名称截断可能产生新的尾点／空格。但它同时用于推导既有分支、立绘路径，贸然改变全局命名可能让旧文件找不到。本轮最终**未改该函数**，不迁移已有命名；命名生成与历史路径迁移需另行一并处理。删除兼容不依赖更改名称。
