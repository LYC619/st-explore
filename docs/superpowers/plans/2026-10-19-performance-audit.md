# ST Explorer 性能审查与优化方案

日期：2026-10-19。2026-10-23 更新：**用户已批准实施，列表与缓存第一批已实现并通过源码与浏览器验证；原生实测及后续批次未完成。** 见 [第一批验证记录](../../verification/2026-10-23-performance-batch-1.md)。下文的“审查时”证据保留为历史基线，不能当作当前结果。

原始请求是整体审查，没有指定某一处卡顿；用户随后明确同意按方案实施。按分批顺序推进，后续持久化和主线程专项仍需其各自测量与验证。

## 1. 结论

建议先做“减少不必要的完整数据读取 + 控制缓存”，随后处理启动索引和大记录写入，最后按测量结果优化长文本计算。当前多个界面已经有分页、虚拟列表或懒加载，主要缺口是这些优化没有贯穿存储层：页面只显示少量内容，底层仍把全库原图或全文取出并克隆。

优先处理这四条路径：

1. 首页、角色库读取全部角色原图；首页快照还长期保留完整角色数组。
2. 单个角色详情通过全库故事读取再过滤；工具、聊天选择器等也有类似路径。
3. 文件库 schema 检查触发全库索引，首次故事列表再读一次相同正文。
4. 完整记录缓存没有容量淘汰，缓存命中仍深克隆完整记录。

这四项相互关联，改善后可同时影响打开速度、切换速度、内存和导入准备时间。不能仅增加缓存，否则可能改善一次切页却加重长期占用。

## 3. 具体发现与建议

### P1-A：首页和角色库的原图读取与保留

**已确认。** `Home.tsx:130`、`Library.tsx:175` 调用 `getAllCharacters()`；首页只挑最近 12 张，角色库默认每页 24 张，分页发生在完整读取之后。`CharacterPortrait.tsx:25` 将整张 PNG 拼成 data URL；`loading="lazy"` 能推迟图片加载/解码，但不能撤回之前已经完成的文件读取和 base64 传输。`Home.tsx:56` 的模块快照保存完整角色列表，离开首页后仍有引用。

**方案：**列表使用专用摘要记录；按当前页或视口请求卡面，建立独立、可限额的缩略图缓存。首页快照只存摘要与最近项 ID。卡面预览可生成派生缩略图，PNG 原件继续供编辑与导出使用，缩略图失效依据原图版本和资料库身份。

现有 `CharacterIndexEntry` 仍保留完整 `card`，里面可能带长描述、内嵌世界书等，不能把换成这个类型等同于完全轻量化。分步推进：先移除全库图片传输，再收窄真正的列表字段。批量导出、编辑、删除确认和回顾编辑都应在操作时读取完整对象，不能把投影当完整记录写回。

### P1-B：详情、选择器、目录查询读完整库

**已确认。** `archive-db.ts:346` 的 `getStoriesByCharacter()` 先 `storyRepo.list()` 再过滤。`CharacterPage.tsx:127` 使用它，且等待结果后结束加载。`Index.tsx:98`、`Tools.tsx:143`、`RegexTool.tsx:126`、`MoveRecordDialog.tsx:37` 也读取全库完整故事；移动记录弹窗还读取全库角色原图。

**方案：**增加按角色/故事 ID 查询的摘要接口，正文仅在选中故事、展开需要正文的区域或执行操作时读取。工具选择器确实使用正文计算游玩时间，不能直接删掉这个展示：需把时间范围等派生值加入摘要，旧记录后台补算。分支摘要需包含 ID、名称、楼数和必要定位字段。

同一方向覆盖 `Home` 资产计数、`GlobalSearch.tsx:37` 和 `AssetLibrary.tsx:171`：目前计数、标题搜索会读取世界书/预设/正则完整负载。优先复用摘要与计数，不在每个组件里分别做一份全量缓存。全局搜索每次重新聚焦会重取目录；可用库版本失效与并发请求合并减少重复读取。

酒馆 `roleplay/catalog.ts:169` 的目录快照仍读取完整角色与故事，包含分支别名等业务逻辑，适合摘要接口稳定后单独接入，保留既有同名隔离和别名规则。

### P1-C：文件库缓存无限保留与重复深克隆

**已确认。** `vault-backend.ts:173` 的 `recCache`、`lightCache` 没有容量或条目淘汰，命中后 `structuredClone`，冷读后再克隆入缓存。全库读取会把大量完整记录留在后端。角色读取还在检查缓存命中之前执行 journal 恢复目录检查（`:188`）；合成库验证了热列表的 N 次目录访问。

**方案：**完整记录与摘要分池，完整记录按估算字节和条目数设双上限，以最近使用顺序淘汰。大于预算的单条记录可供当前调用者使用但不进入保留缓存。图片独立计费；相同 ID/版本并发读取合并；库切换、写入、删除和移动按现有版本边界失效。

保留调用者对象与缓存不共享可变引用的契约；不全局删除 `structuredClone`。减少“被克隆的数据”优先于减少隔离。恢复检查只有在引入明确的“该库/角色已完成恢复且没有新 journal”状态、并覆盖新增 journal 和失败重试之后，才可去重，不能跳过恢复来提速。

第一阶段先记录容量分布再确定预算。成功标准是完整缓存不随已访问故事数无限增长；当前打开的超大故事、活动聊天和编辑草稿不应被误算为可随意丢弃的缓存。

### P1-D：启动检查和故事轻量列表反复读正文

**已确认。** `MigrationNotice` 调用 `getArchiveSchemaVersion()`，后者通过 Repo `get()` 进入 `ensureIndex()`。`vault-backend.ts:270` 扫描各类记录，`:313` 为取得 ID 整读故事；这些对象不填充轻量池。`:456` 随后的 `listLight()` 又整读故事再丢弃正文。

**方案分两步：**

1. 保留迁移与维护恢复门槛，给固定位置的库元信息提供专门读取路径；索引扫描既然读过正文，就即时生成小摘要，避免本次启动再读。不要把整篇正文塞进永久缓存解决重复扫描。
2. 建立可重建的目录摘要缓存，存路径、ID、归属、排序/筛选字段、分支目录及文件签名。启动先校验目录与变更文件，正文按需加载；缺失、损坏或版本不兼容时回退重建。

摘要是派生缓存，`故事.json` 继续为真源。重命名、跨角色移动、删除后保留文件、外部编辑、备份恢复、崩溃恢复都必须覆盖。若仅用 size+mtime，会有同大小同时间替换的漏检边界，需明确增量校验和手动/必要时全量重建策略，不能用失效不完整的缓存换取“秒开”。

### P2-A：记录查看状态仍整篇写入，且挡住首屏

**已确认。** `StoryWorkspace.tsx:170` 在 `setStory` 之前等待 `updateArchiveStory`；`vault-backend.ts:537` 始终序列化并写入完整 `故事.json`。`derivedUnchanged` 已经避免重写主线/分支 JSONL，但不能避免主记录的大写入。

**近期方案：**先展示已读取内容，将访问状态写入与首屏解耦，并保留串行队列、错误提示、切页 flush 和库/故事身份校验。高频访问状态可合并，真实编辑保存不能被合并丢失。

**后续方案：**若大故事实测写入成本仍高，再设计独立阅读状态记录，覆盖备份、迁移、排序和恢复后再实施。它改变持久化模型，不能混入第一批当作小修。长故事正文或某个分支修改时，目前也会重建多份派生文件；可按主线/分支内容版本只更新变化的派生物，保持导出与工作副本一致。

### P2-B：长聊天的虚拟化没有减少全量预处理

**代码确认，用户规模下收益待测。** `ChatPreview.tsx:470` 在 `session.messages` 或规则变化后同步对全部消息应用正则、分段；`NovelView.tsx:192` 构建全篇小说文档，随后全量分页并 stringify 章节用于签名。虚拟化限制的是 DOM 数量，这些前置计算仍可能阻塞主线程。

**方案：**先测 500 / 2,000 / 10,000 楼的导入、改单楼、切 swipe、切隐藏楼、改规则、改字号。对单楼修改复用未变化的处理结果；规则变化等全局操作采用可取消的分批任务或 Worker。缓存键必须包含消息内容/版本、规则版本、深度条件与显示选项；新增一楼会改变旧楼的 depth，不能简单只处理最后一楼。发言人连续关系单独重算。小说翻页和缩放必须保留当前 messageId/段内位置。

`regex-processor.ts` 已缓存编译后的正则，故“加正则编译缓存”不是新收益点。Worker 的目的首先是让界面可响应，不保证总耗时降低；大文本传输、复制和取消过期结果也要计量。

### P2-C：酒馆首次打开与分词

**代码/构建确认，运行瓶颈待测。** 路由已经按需加载；`tokenizer.ts:1` 静态引入两套编码词表，宿主、Agent 和上下文台账有同步编码路径。`count-prefix-batch` 逐次编码越来越长的前缀，长输入可能产生明显重复工作。

**方案：**分开测 STE 宿主模块解析、iframe 初始化、插件就绪和分词。按实际模型加载对应词表；高成本编码可进入专用 Worker，并保留精确结果一致性。不能把各片段 token 数直接相加替代拼接后编码，边界分词可能变化。目录查询复用 P1-B 的摘要。

后台聊天常驻是已经存在的行为约定，不能靠切页即销毁聊天换取内存下降。保留生成与保存，评估隐藏后的非必要界面工作。关闭后的宿主清理代码已经存在，仍需测 JS 堆、iframe 和 WebView2 多进程总占用是否稳定。

### P2-D：ST 导入与批量处理

**代码确认，端到端收益待测。** `st-import.ts:952` 起，为按来源去重读取完整角色、完整故事及资产；导入器在选中的关系处理和文件写入上顺序执行。角色库手工批量导入使用 `Promise.allSettled(selectedFiles.map(...))` 同时准备所有选择文件，巨大批次可能抬高瞬时占用。

**方案：**按来源路径构建摘要索引，仅把本次需要校验/更新的对象读为完整记录。文件读取与解析按字节预算限制并发；独立任务可流水处理，有关联的世界书关系重建与写入顺序保留。手工多图导入也设准备队列。

扫描、解析、预览、提交分别计量；保持 ST 来源只读、路径校验、取消后的已完成项说明和损坏文件关系保护。已有立绘下载有并发上限、后台任务与预览缓存，本轮不建议泛化为“所有下载提高并发”。

### P3：按规模触发的列表、草稿和备份专项

- 角色库默认 24 项已有分页；“全部”及展开分组后才需要评估网格/列表虚拟化。保留批量选择、键盘操作和回到原位置，避免全局导航改版。
- 世界书会话已有 400ms 防抖、自动保存已有 600ms 延迟，但仍全量 stringify，会话与失败恢复还涉及浏览器存储容量。大书实测后再评估异步草稿存储，不能改成仅存 ID 丢弃未保存内容。
- Web/Android 的 `idb-repo.ts:98` 全量 `getAll()`，`listLight` 直接等于 `list`。仅收窄 TypeScript 类型或改成遍历游标不会获得真正的字段投影；需要在同一事务维护独立摘要 store，旧库可重建。
- JSON 备份会读取全部数据再序列化；阅读包已有 Worker。备份属于低频且有完整性要求的路径，测峰值后再决定流式处理，不作为第一批。

## 4. 路线选择

| 路线 | 适用范围 | 取舍 |
| --- | --- | --- |
| 仅做局部缓存、memo、增加延迟加载 | 少量界面热点 | 改动较小，但难以消除全库读写，缓存可能增加内存 |
| **按需读取 + 有界缓存 + 派生摘要，分批推进（推荐）** | 当前文件库与浏览/整理工作流 | 可逐入口验收，保留现有文件真源；需认真维护摘要失效 |
| 全面换数据库、重写状态层/阅读器 | 未来数据规模明显超出现结构时 | 涉及迁移和大量兼容工作；当前证据不足以支持全面重构 |

## 6. 验收规则

首先用读取/写入/克隆次数等结构性断言消除无效工作，再比较用户体感指标。不能只验证源码出现 `memo` 或组件被 mock 后的测试通过。

建议量测矩阵：100 / 500 / 2,000 个角色；500 / 2,000 / 10,000 楼聊天；单张图按 256 KiB / 2 MiB 档，分批运行，避免最高档组合占满机器。先记录测试机 RAM、CPU、磁盘、浏览器/WebView2 版本、源码 SHA、构建模式。不要用特意缩小的正文代替“楼数相同”的大聊天。

每个交互进行预热后至少 10 次，报告中位数与最慢一次；需要 p95 时至少采集 30 次，不把一两次运行称为分位数。冷启动至少 5 次，同时说明 OS 文件缓存状态；不可通过未声明的缓存预热美化结果。

建议指标预算（是后续验收目标，不是当前成绩）：

- 常规搜索、筛选和切页的输入响应优先控制在 100ms 内；长任务使用浏览器 50ms 标记定位，并单独报告超过 200ms 的阻塞。
- 稳定合成库中主要路径的耗时与峰值应有可重复改善；允许给定误差的回归阈值在批次 0 实测后固定。
- 连续 20 次“首页 → 角色 → 故事 → 返回”、酒馆打开/关闭、切库后，记录 GC 后 JS 保留堆及 WebView2 总工作集趋势；预算内缓存可保留，但不能随访问次数持续增加。
- 错误、取消、关窗、返回、切库、并发生成与保存均有用例；原件/工作副本/导出副本各自校验。界面进入、操作、保存、返回、状态恢复完整走查。

浏览器、Tauri、Android 分开报告。缓存计数、JS 堆、进程内存、图片解码/GPU 资源、安装包大小分别说明，不能相互替代。
