## 1. 用户实际获得的能力

用户在沿用 ST 原始交互的聊天界面中打开已有故事，发一条消息，主模型继续扮演。开启 Agent 后，工具 Agent 自动识别本轮涉及的人物、地点、事件，搜索并读取世界书和本地记忆，将必要资料、文风和叙事连续性提醒送到主模型，回复完成后维护记忆。

主模型承担长历史和正文生成。工具 Agent 初始只接收当前输入、有限近期上下文、当前状态和可搜索的目录，缺资料时继续调用工具。两者可以使用同一个提供商，也可以分别选择模型；主模型不需要支持工具调用。

无 Agent 模式使用同一个聊天界面、故事数据、编辑、候选回复、分支和导出，按已验收的 ST 预设、世界书和正则语义生成。可选记忆插件仍可能调用摘要模型；“无 Agent”表示没有 STE 工具 Agent，并不禁止插件自己的模型请求。

常用脚本、变量、交互式内容等能力进入统一宿主。用户不用围绕一组彼此接管界面的插件配置才能开始聊天。

### 1.1 原始界面与 STE 能力的结合

以 TauriTavern 保留的 ST 前端源码、样式、模块和实际交互作为游玩界面基底。沿用顶部功能入口、抽屉、消息操作、候选回复、预设、世界书和扩展面板，再逐项增强内容；不以 React 重画一套外观相似的聊天界面替代此路线。

| 用户熟悉的入口 | STE 接入内容 |
| --- | --- |
| 角色管理 | 接入现有角色库、标签、资产关联与编辑能力 |
| 聊天记录与消息操作 | 接入故事、分支、归档、备份及同一份正文数据 |
| 世界书 | 保留蓝灯/绿灯和条目编辑，增加来源、剧情版本和接受新版本 |
| API 与预设设置 | 沿用 ST 操作，绑定 STE 现有连接配置；增加工具模型配置 |
| 扩展设置 | 内置酒馆助手常用能力，优先验收柏宝书 |
| 聊天中的记忆入口 | 查看和修正故事笔记、文风规则及本轮引用资料；默认收起 |

普通模式和 Agent 模式使用同一套聊天界面。Agent 在发送流程中自动运行，不另设需要手工操作的 Agent 工作台。STE 现有管理功能按上述入口衔接，避免玩家在两套角色、聊天或连接设置间反复维护。

上游结构提供现成的界面分区，但各功能仍有共享状态和请求依赖。先保留成熟交互，再按模块改善检索、批量管理、记忆与世界书版本；能节省界面设计和重复实现，整合成本仍需按实际依赖核对。

## 4. 架构与职责

~~~mermaid

    UI[ST/TauriTavern 原始聊天界面] --> K[统一生成生命周期与 STE 提交边界]
    K --> C[上下文组装]
    C --> ST[无 Agent：沿用上游生成组装与扩展]
    C --> AG[Agent：工具 Agent 检索与提醒]

    ST --> P[主模型请求]

    P --> K
    K --> S[现有故事仓储]
    S --> POST[采纳回复后的记忆更新]
~~~

### 4.1 聊天运行时

负责一次生成的身份、状态、取消、正文提交和后续记忆任务。界面、脚本和工具都调用同一个入口；只有运行时提交正文。普通模型请求与工具 Agent 请求共享 Provider 传输层，但请求上下文彼此独立。

前端沿用 ST 的 canonical chat[]、chatMetadata 和事件契约；它们是当前故事的内存工作状态，STE 的 ArchiveStory/ChatSession 仍为持久化正文模型。适配层维护 ST 楼层/候选与 STE 稳定 ID、分支、来源修订的对应关系，所有正文保存汇入一个提交入口。不得让 TauriTavern 原仓储与 STE 各自保存一份正文再双向同步；JSONL 继续作为约定的导入导出/派生格式。保留上游自动保存行为时，将其接入同一源故事队列。

普通模式保留上游预设、世界书、宏和正则的生成路径；Agent 模式在同一发送生命周期中接入资料准备与冻结上下文组装。上游的流式显示、停止和候选操作仍统一处理。具体 hook 必须在来源锁定后验证，不能仅靠请求拦截假定已经接管了生成前处理和保存后事件。

运行状态：准备 → 检索（仅 Agent）→ 正文流式生成 → 正文保存 → 记忆更新 → 完成。取消、失败、保存待恢复为明确状态。记忆更新失败不把已保存正文变回未保存。

一次任务捕获 vaultSessionId、源 Repo、storyId、branchId、branchRevision、turnId 和 AbortSignal。branchRevision 只在影响后续生成的输入变化时增加，阅读位置、收藏等不增加；消息编辑、候选切换、分支内容、有效资产和生成变量变化会增加。切库再切回也产生新的 vaultSessionId。

首版切故事、分支或库时取消前台生成；返回后的迟到片段按任务身份丢弃。已经持久化的正文保留。生成期间编辑历史会取消该轮生成，更新历史后重新发起；不向被改写的历史提交旧回复。

### 4.2 共享能力层

消息读取与修改、变量、世界书读取、受控资产变更、原文检索、模型调用、资料注入和事件订阅集中实现一次。工具 Agent 使用工具封装，内置功能直接调用，兼容插件通过适配器调用。

Provider 客户端、文件库与副作用执行由 STE 持有。第三方脚本不获得宿主原生文件命令或全局密钥对象。是否允许脚本读取某个故事、发模型请求或修改变量，在启用该脚本时建立范围；聊天过程中沿用该范围。

### 4.3 Agent 引擎选择

实际采用 STE 自有的有界工具循环，复用现有 Provider 传输、取消和用量处理。TauriTavern 原 Agent 路由在接入层禁用，避免与主模型/工具 Agent 的分工重复；未引入 Pi 或其他完整 Agent 框架。

循环最多执行 6 轮模型决策和 12 次工具调用。故事、记忆、权限、缓存记录和提交逻辑均由 STE 管理，产品不依赖常驻 Node 服务。浏览器中的工具往返、取消、最终请求和保存后维护已验证；远端模型协议仍需按实际连接验收。

## 5. 两种模式与缓存

| 行为 | 无 Agent | Agent |
| --- | --- | --- |
| 主模型 | 普通文本生成即可 | 普通文本生成即可 |
| 工具模型 | 不需要 | 选择支持工具协议的模型，可与主模型共用提供商 |
| 世界书 | ST 关键词、条件、位置、预算与递归规则 | 稳定蓝灯资料＋工具 Agent 选择的本轮绿灯原文 |
| 记忆 | 可不用，或由已适配的柏宝书等插件维护 | STE 文件记忆自动维护 |
| 动态注入 | 按 ST 深度与插件契约 | 默认按回合追加并固定 |
| 缓存目标 | 在兼容行为下尽量复用 | 在同一上下文周期内保持已发送前缀 |

### 5.1 Agent 请求如何增长

每个上下文周期记录初始稳定资料、Provider/模型和影响序列化的配置。蓝灯、角色卡、文风基础约定在周期开始时形成快照。之后保存每轮的实际资料包、用户消息和已采纳回复，不在每轮重建旧资料包。

~~~text
稳定初始资料
第 1 轮：用户消息 → 固定资料包 → 采纳回复
第 2 轮：用户消息 → 固定资料包 → 采纳回复
第 3 轮：新用户消息 → 新资料包 → 正文生成
~~~

资料包按“给模型的背景资料”明确标识，不伪装成用户指令。Provider 适配器负责表达该角色；若需与当前用户内容合并，应在本轮首次发送时完成并固定。主模型不接收工具调用轨迹、文件写入命令或填表规则。

运行记录以增量段保存，不在磁盘上每轮复制全量历史。检查器比较最终 Provider 请求的历史消息、角色、内容、顺序及相关配置，而不只比较主提示词字符串。Provider 不提供缓存统计时显示“未报告”，不以本地前缀相同比例冒充服务端命中率。

修改历史、切换候选、改变预设布局/Provider 或启用会重排历史的扩展，会建立新的上下文周期并记录原因。首版无 Agent 模式保留 ST 深度注入，Agent 模式的动态资料按回合追加；未额外提供 Agent 深度注入兼容开关。原预设的尾部指令仍保留在本轮资料之后，其变化也参与实际前缀检查。

旧资料包注明生效回合，最新资料只声明当前状态和必要修正。历史地点、伤势等不被误读为现在仍然有效。新世界书版本通过后续资料表达，过去的初始快照继续可追溯。

### 5.2 长历史的边界

首版由原 ST 提示词组装按配置窗口选取可容纳的历史，并为冻结资料预留空间。窗口滑动使旧请求前缀不再成立时，建立新的上下文周期并显示原因；完整故事仍在仓储中，可供工具 Agent 检索原文。独立的换章界面与自动多层章节摘要未在首版实现。缓存降低重复输入处理成本，不增加模型窗口，也不自动保证长文注意力。

## 6. 本地文件记忆

### 6.1 内容与文件

桌面端在现有故事目录内保存，路径按故事 ID 经 pathOf 定位。分支目录用稳定 ID；主线使用保留的 main 标识，普通分支加 branch- 前缀，避免名称冲突。

~~~text
<故事目录>/
  故事.json                           # 正文唯一真源
  聊天.jsonl                         # 现有 ST 派生文件
  memory/<分支键>/
    index.md                         # 可重建的目录、主题和短描述
    state.md                         # 当前场景、时间、在场人物、即时状态
    characters/<人物ID>.md           # 身份、关系、角色所知与来源
    events/<事件ID>.md               # 已发生事件、时间顺序与原文引用
    threads/<线索ID>.md              # 约定、目标、悬念及解决情况
    style.md                         # 文风约定、范例原文引用
  .ste-control/roleplay/<分支键>/
    turns/<回合ID>.json               # 本轮资料、上下文周期、提交状态和引用
    memory-journal/<操作ID>.json      # 可恢复的记忆增量
    worldbook-versions/<条目ID>/      # 分支内设定版本与接受状态
~~~

文件按需创建；不为每一回合重写所有人物文件。使用现有 frontmatter 格式，至少保存 id、kind、revision、sourceRefs、validFrom、status；正文保持人类可读。每个 sourceRef 包含消息 ID、候选标识、正文摘要值和依赖历史摘要值。下标只用于显示和 ST 映射。

Markdown 文件是当前记忆内容的权威，提交日志保留增量与前后版本供恢复/撤回；index 和检索索引可随时重建。事实最终可追溯到故事原文或用户手动记录，摘要和模型建议不能自行变成事实来源。

事件与状态分开：事件记录“发生了什么”，state/人物记录“现在是什么情况”。伏笔状态区分 open、resolved、cancelled、failed。未经证实的猜测写入建议或不确定信息，不能写成已经发生的事件。角色知识明确记录知情者；叙述者知识不默认传播给所有人物。

文风保留具体规则和少量用户认可的原文锚点，按场景取用。叙事提醒关注未兑现约定、视角、节奏和连续性，默认提供建议，不预先决定用户行动或强制下一段剧情。

### 6.2 更新与恢复

生成前阶段只读记忆与世界书，允许形成待用资料；剧情事实在当前采纳回复保存后才做增量维护。新回复默认是当前选中候选，用户不需要逐条点确认。重新生成、swipe、正文编辑、删除会触发失效检查。

记忆写入流程：读取当前版本 → 生成带来源的增量 → 在源故事队列内核对任务身份与来源 → 写 prepared 日志 → 原子替换受影响文件 → 标记 committed → 刷新目录。重试以操作 ID 幂等，不能重复扣物品或重复创建事件。

单文件原子写不等于多文件事务。重启发现 prepared 日志时，根据前后文件摘要和正文提交状态恢复；无法判定时保留两份，暂停该记忆写入并提供恢复入口，正文仍可读取。

首版采用保守失效边界：从最早改变的剧情来源开始，后续自动记忆变更重新核对/重算。用户手工记录保留并标记冲突。后续再按实际性能需要缩小失效范围，不先引入复杂依赖图。

外部编辑 memory 文件在下次读取/写入前核对内容摘要；不以进程内缓存覆盖磁盘。检测到手工改动后记录 manual 修订，更新索引；Agent 写入遇到旧 revision 时重新读取。不可解析元数据保留原文件并报告具体文件。

下一轮若上一轮记忆更新尚未结束，先等待同分支写入屏障；若更新失败，读取最后一致版本并补读未归档的近期原文，显示“记忆待补全”。不得将半写入状态交给主模型。

### 6.3 平台与迁移

桌面直接使用 VaultFs。Web 与当前 Android 仓储通过同一 RuntimeStore 接口保存相同逻辑记录，可用已有本地存储后端；不声称它们已有用户可见的 Vault 目录。导出完整故事包时统一输出上述文件结构，导入时按 ID 和来源映射恢复。

普通 ST JSONL 导出继续保留必要的原始/插件字段，不混入 STE 的隐藏工具消息。完整备份必须包含 memory、运行记录和版本资料；单独导出 JSONL 不宣称带走全部 STE 长期记忆。索引和临时草稿不作为恢复所必需的数据。

## 7. 世界书与资产演化

蓝灯/绿灯是激活策略，与条目的插入位置是两个维度。无 Agent 模式按 ST 原语义处理 constant、关键词、次级条件、概率、组、冷却、持续、递归、深度及预算。无法解释的生成字段在发送前具体列出，不悄悄忽略后宣称兼容。

Agent 模式先以人物、地点和事件索引找候选，再由工具 Agent 按需读取原条目；记忆帮助定位，不强制把世界书全部改写为摘要。检索结果附条目 ID、版本和相关理由；主模型收到原文及必要说明。

日常状态变化写 memory。持久设定变化形成世界书版本草稿，包含 baseEntryId、version、branchId、validFrom、sourceRefs 和 accepted 状态。原件保留，同一作用域/时间只有一个已接受版本有效。用户原始世界书、角色卡和预设的修改遵守现有预览接受边界；自动维护的记忆无需逐条确认。

## 8. 内置能力与插件兼容

### 8.1 三种集成路径

| 路径 | 收益 | 代价与决定 |
| --- | --- | --- |
| 原始 ST/TauriTavern 前端＋STE 统一数据与能力接入 | 保留熟悉界面、成熟功能模块和真实扩展上下文 | 用户已选择；固定上游版本，接入同一故事与配置来源，逐项验收 |
| 现有 React 聊天页＋重新实现 ST 接口 | 可延续原组件体系 | 已被用户本轮调整替代，不再按此路线新建游玩界面 |
| 两套完整应用各自运行、各自存档 | 可分别启动原产品 | 产生双份状态与同步责任，不作为当前整合方案 |

直接集成包括真实复用上游前端和成熟功能，以及将其存储、请求和扩展能力接入 STE。新增代码集中在接入边界和产品增强，避免另写同功能解释器或伪造全套 ST 上下文。实际复用源码仍须记录来源与许可；插件是否可用按真实功能验收。

### 8.2 首轮内置能力

下表区分原版界面能力与内置助手的实际开放范围。可调用的助手函数以[兼容说明](../../principles/extension-compatibility.md)为准；原版 ST 存在某个扩展接口，并不表示沙箱脚本也能调用它。

| 能力 | 统一宿主行为 | 首轮范围 |
| --- | --- | --- |
| 消息与候选读写 | 稳定 ID 与 ST 楼层映射，写入走故事队列 | 原界面负责创建和候选切换；助手可读取候选、编辑消息和隐藏状态 |
| 变量 | chat/message/global/script 作用域 | 同步快照读取、基线冲突检查和保存屏障；分支变量隔离，全局变量按资料库共享 |
| 事件 | 有序订阅、可等待事件、清理与取消 | 生成、提交、编辑、swipe、切故事；不因虚拟列表重复挂载而重复总结 |
| 资料注入 | 无 Agent 保留原版扩展槽位；Agent 收集并冻结本轮资料 | 原版模块与柏宝书使用原接口；首轮助手沙箱不开放完整注入 API |
| 模型请求 | 统一 Provider、队列、取消和用量 | 助手 generate/generateRaw 为非流式工具请求，不递归触发整个 Agent 流程 |
| 正则与宏 | 沿用上游执行器，接入 STE 资产；显示处理与发送处理分开 | 用固定样本核对宏、正则作用域、顺序及原文保留 |
| HTML/JS 内容 | 静态 Markdown/HTML 与动态脚本分开 | 批准启用的脚本、变量面板和交互代码块 |
| 常用斜杠命令 | 原界面沿用上游解析器；助手入口按能力限制命令 | 原界面分支命令实测；助手支持限定的变量/文本命令，完整列表见兼容说明 |

公共 API 的同步/异步语义须分别保留。酒馆助手 getVariables/replaceVariables 是同步调用，不能随意变成 Promise；受控运行区采用作用域快照和显式落盘屏障，异步生成仍返回 Promise。保留上游 DOM 与模块能减少适配工作，但依赖特定版本内部模块、额外后端或原生平台接口的脚本仍须实测。

真实 ST 扩展上下文通过宿主适配访问 STE 数据；动态内容 iframe 沿用已验证的桥接与挂载契约。同页扩展可能直接修改 chat[]，因此生成前、提交前必须核对实际正文和来源，不能只依赖插件是否发出预期事件。合法历史修改触发正常来源失效；在 Agent 模式下同时从变更位置重建相应上下文周期，不把旧冻结片段静默改写。

### 8.3 柏宝书兼容样板

固定目标为 1.2.7 / 5c8a6b60d8c1185e169c46d43f63fce7d35d8583。优先验收自动摘要、人物/物品/场景/悬念、隐藏旧楼、摘要注入、编辑、候选切换与数据往返。

真实依赖包括 SillyTavern.getContext、chat/chatMetadata、saveChat/saveMetadata、extensionSettings、生成事件和拦截器、setExtensionPrompt、generateRaw/连接管理、部分 DOM 与动态 ST 模块。优先由继承的真实 ST 环境提供这些能力；其保存、连接与后端代理路径须接入 STE，并验证事件顺序和数据往返，不能只凭前端已启动宣布兼容。

首轮兼容明确关闭其可选向量功能：该功能额外依赖 Embedding/Rerank 与 /api/plugins/baibaoku/v1 后端。实现其向量后端等价接口是独立扩展包，不是自动摘要验收的一部分。

兼容记录按功能标记“已验证、需适配、不支持”，记录版本和样本。使用用户提供或自行取得的合法插件包做运行验证；不能在未获明确授权时把柏宝书源码改造后随 STE 发布。

### 8.4 记忆维护只有一个负责方

每个故事分支选择 native-agent、baibai 或 none 作为自动记忆维护者。Agent 默认使用 native-agent；无 Agent 可选 baibai。切模式只切维护策略，不删除另一方数据。旧记忆可通过只读适配器提供给当前检索，再由用户选择迁移。

避免内置记忆与插件同时总结同一回复、同时隐藏历史或重复注入。其他已启用脚本仍可做渲染、变量和工具请求；事件按来源标识，工具请求不会再次被当作角色回复处理。

## 9. 功能与性能统一的具体做法

- 沿用并验证 TauriTavern 的聊天渲染和挂载管理；游玩聊天 DOM 只有一个拥有者。动态 iframe 的挂载、释放和状态恢复遵守锁定版本及指定插件的契约，验证离屏/卸载清理，避免 React 再管理同一段 DOM。
- 流式阶段复用上游显示路径；动态脚本采用已验证的启动时机，避免每个 token 重建 iframe 或重复执行脚本。
- 记忆更新只写受影响文件；目录/关键词索引按变化更新，Embedding 属于可选索引后端。
- 主请求和工具请求共用连接配置、取消链与用量记录；一次普通角色回复只提交一条主回复。
- 用户看到的状态保持简短：准备资料、生成中、记忆更新中、需重试。技术轨迹放在按需展开的详情中。
- 工具循环设最大轮数、调用数、检索字数和时间预算，限制异常循环；预算用尽时返回已有证据与缺失信息，不编造检索结果。

初始调优参数作为实现时的可配置默认值：近期上下文 4 对消息、工具工作上下文目标 8k token、本轮资料目标 2k token、最多 6 个模型决策轮次/12 次工具调用。世界书原文超出目标时按相关性和可用窗口调整，硬上限按用户模型窗口及输出预留计算。参数不能作为回复质量保证。

性能验证使用相同故事和机器分别记录普通模式、Agent 模式及启用脚本后的本地耗时、首字延迟、DOM/iframe 数和读写量。模型网络耗时单独计量。第一轮目标为 2,000 楼样本中 iframe 数受虚拟窗口限制、切换 50 次无监听增长、不发生每 token 整故事落盘；具体毫秒门槛在 P1 基线测量后写入验收记录。

## 10. 异常与用户操作

| 情况 | 行为 |
| --- | --- |
| 工具 Agent 超时/报错 | 保留诊断，提供重试准备或使用已有确定资料继续；不隐瞒缺资料 |
| 主模型不支持工具调用 | 正常使用主生成；工具由另一通道完成 |
| 工具模型不支持工具协议 | 在启用 Agent 时报告能力缺失；无 Agent 仍可用 |
| 主生成中断 | 沿用原版停止行为，保存当前采用的部分正文；该轮未成功结束，不自动据此维护事实记忆 |
| 正文保存失败 | 显示未保存草稿，禁止启动该回复的记忆维护 |
| 记忆写入失败 | 已保存正文保留，日志允许幂等恢复，下一轮使用最后一致状态和近期原文 |
| swipe/编辑/删楼 | 增加分支修订，失效后续来源和相应缓存段，重算自动记忆 |
| 世界书或预设原件有改动 | 对未来生效的版本/周期做显式切换，过去记录可回查 |
| 插件缺少 API | 给出具体能力与版本，不以空函数假装成功 |
| 关闭插件/切库 | 注销事件、一次性注入和动态页面，迟到任务不能写入新目标 |
